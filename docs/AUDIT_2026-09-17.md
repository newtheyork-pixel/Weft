Source: 15 code readers plus two independent verifiers per bug (audit workflow wf_7d684bd1-af6, paused before every bug was verified). Status meanings: VERIFIED = two verifiers agreed it is real; PLAUSIBLE = verifiers split; UNVERIFIED = reported, verification not yet run; REFUTED = verifiers agreed it is not a bug.

- **[C] No session-token refresh: after 60 minutes every PDF fetch and every "Try again" fails permanently (SupabaseManager.swift:122)**  
  perform() now owns the session lifecycle (commit a8ca566). setSession stores expires_in as a refresh deadline at 80% of the advertised lifetime (about 48 min on the default hour); every request refreshes proactively past that deadline and re-stamps the Authorization header it already built. If the server rejects the token anyway, the request refreshes once and retries with the new token: a 401 counts as a token rejection, as does a 400/403 whose body names the JWT (Supabase Storage answers that way), while a plain 403 from RLS does not, so an RLS refusal still surfaces as itself. New refreshSession() posts grant_type=refresh_token, stores the rotated pair (falling back to the token it sent when GoTrue omits a new one), and is single-flight via a stored Task so a class worth of requests noticing the same expiring token share one round-trip instead of invalidating each other's rotation. exchangeCode and the refresh call itself pass allowRefresh: false so they cannot recurse. A failed refresh deliberately does NOT clear the session (signing a student out mid-exam is worse than one failed request) and backs the next attempt off 30 s.

## Features lost since the Electron app

The retired Electron app (Tessera/main.js, 3,034 lines, plus renderer/student.js 1,922 and renderer/teacher.js 1,903) was a proctoring-heavy shell: five "hardening categories" that shell out to launchctl/chflags/codesign/system_profiler/route/ifconfig, a startup tamper guard (DYLD env vars + app.asar SHA-256), a 15 s mid-exam re-sweep with blackout, 20 s screenshots, 15 s webcam stills, a 5 s heartbeat, a same-public-IP-as-teacher check, VPN/tether route analysis, virtual-display (Sidecar/AirPlay/DisplayLink) detection, a "close them for me" process killer, a sudo "disable Chrome Remote Desktop" button, Blackbaud OAuth/sections/assignment import, and a Supabase-realtime teacher roster with per-student screenshot grids.

The native app (Weft/Weft/*.swift, 12,582 lines) kept the shape and dropped almost all of the remediation and evidence layers, deliberately and documented in ROADMAP.md: webcam dropped, screenshots deprioritized, no heartbeat, no launchd/sudo/codesign hardening, no IP matching, no virtual-display detection. Third, several teacher-facing controls are unwired mocks (file attach, Blackbaud import, per-link scope), and the live roster never refreshes after launch. ## Data layer and speed

Weft's native data layer is one @MainActor @Observable store (AppState.swift, 1534 lines) sitting on a hand-rolled URLSession Supabase client (SupabaseManager.swift, 1202 lines): PostgREST rows/insert/update/upsert/delete helpers, an RPC layer, Edge Functions, Storage, and GoTrue PKCE OAuth opened in the default browser. Models.swift holds Codable DTOs with deliberately tolerant decoders plus the bundled mock samples that keep every screen populated until sign-in. WeftApp.swift is a single-Window scene with three switch-based routers and the Sparkle updater.

The decisive speed finding is a build setting, not a line of code. Weft.xcodeproj sets SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor (project.pbxproj:308, 353), so every unannotated type in the module, including SupabaseManager, ProctoringEngine and PDFLoader, is main-actor isolated. The ten "no async operations occur within await" warnings the task cites (SupabaseManager.swift:181, 197, 222, 240, 256, 406, 422, 437, 826, 859) are the compiler proving it: await headers() suspends nothing because the caller is already on MainActor. I reproduced all ten plus the AppState.swift:638 isolation warnings with a clean xcodebuild. Consequence: every JSONEncoder.encode, JSONDecoder.decode, JSONSerialization call and httpBody assignment runs on the typing thread, including the full essay HTML every 0.8 seconds and every essay in a grading session.

Everything else compounds that. Loads fan out serially (loadTeacherHome is five sequential round trips, loadOutlineState is an N+1 loop of three hops per active row, startWriting duplicates lookupSession and getTest), nothing is cached across navigation, neither home view has a loading state so the "you have nothing" empty state renders during every load, saving one grade refetches every essay in the session, and two separate flows block up to eight seconds on api.ipify.org for a public IP the native app documents that it never compares. There is no token refresh, no session persistence, no retry policy, no request timeout, and no draft restore.

## Release and download pipeline

The chain is: a static site button links to /api/download?arch=..., a Vercel Node function asks the GitHub API for the newest release on newtheyork-pixel/weft-releases, picks an asset and 302s to it; the user installs a notarized DMG; the installed app runs Sparkle 2.9.3, which polls SUFeedURL (raw.githubusercontent.com/.../main/appcast.xml) every 86400s and verifies each enclosure against SUPublicEDKey. scripts/release.sh is the only producer: it reads MARKETING_VERSION from the project, derives CFBundleVersion from `git rev-list --count HEAD`, archives Release, exports Developer ID via scripts/exportOptions.plist, builds a styled DMG with dmgbuild, notarizes and staples, optionally runs Sparkle's generate_appcast over a zip of the app, publishes both assets to a GitHub release, then commits appcast.xml to the releases repo default branch. The student portal is a single-page, no-build ES module. /portal/index.html ships static chrome (header, footer, skip link), about 340 lines of portal-scoped CSS whose class names are an explicit contract with portal.js, a static loading skeleton, and a noscript fallback. portal.js (715 lines) imports @supabase/supabase-js@2 as an unpinned ESM bundle from cdn.jsdelivr.net, creates a client against project elrrvicxsguqstqciodn with the publishable key, and keeps all state in four module globals: user, currentUserId, homeCache, busySessions. ## Exam editor and typing

The native writing surface is an NSTextView (WeftTextView, a TextKit 2 view) inside an NSScrollView, wrapped by the RichTextEditor NSViewRepresentable. A @MainActor @Observable RichTextController owns document access: the text view holds the essay, the controller exposes wordCount, setContent, snapshot and htmlSnapshot, and every formatting command (bold, italic, underline, H1/H2/Body, bullet and numbered lists, font family, size, text colour, highlight, line spacing) mutates the NSTextStorage directly after declaring the edit with shouldChangeText. Lists are implemented as literal "\t<marker>\t" text plus an NSTextList in the paragraph style; the marker prefix is stripped again by the word counter and by the HTML serialiser. WeftTextView adds Google Docs key equivalents (Cmd+B/I/U, Cmd+Alt+1/2/0, Cmd+Shift+7/8), Return and Tab list behaviour, and a layout() hack that clamps the NSTextInsertionIndicator frame because double spacing is implemented with lineHeightMultiple. RichTextHTML serialises the document to the Electron-compatible tag subset, inferring h1/h2 from the first character's point size. ExamView hosts the editor in an HSplitView beside the reference panel, owns the countdown (TimelineView anchored to .now), the proctoring monitor loop, the submit flow, and autosave: every textDidChange recounts words over the whole document and calls scheduleSave, which unconditionally writes runtime.saveState, bumps a @State generation counter, cancels the previous Task and starts a new 0.8 s debounce that upserts the full HTML into essay_submissions. There is no draft restore, no on-disk durability, no first-responder handling, no paste or context-menu policy, and Apple Intelligence Writing Tools and inline predictions are left at their enabled defaults inside a product that is explicitly anti-AI.

## Website claims versus what the code does

The two marketing pages make roughly 60 checkable factual claims about the shipped native app. I extracted every one and traced it into Weft/Weft/*.swift, the Supabase migrations, the release script and the download function.

A solid majority verify TRUE against code. ## Sign-in and sessions

Weft's native sign-in is a hand-rolled GoTrue PKCE flow with no Supabase SDK. SignInView shows one "Sign in with Google" button which calls AppState.signInWithGoogle, which calls SupabaseManager.signInWithGoogle (SupabaseManager.swift:918). That mints a 32-byte verifier plus S256 challenge (PKCE enum, line 1138), builds GoTrue /auth/v1/authorize with provider=google, prompt=select_account and redirect_to=https://weft.optimizegrade.com/auth-finish, opens it in the user's DEFAULT BROWSER via NSWorkspace (deliberately not ASWebAuthenticationSession, so the school Google cookie is reused), then parks a CheckedContinuation. Google returns to Supabase, Supabase 302s to the static auth-finish page, whose inline script does location.replace('weftnative://auth-callback?code=...') and, after 1200ms, reveals a manual "Open Weft" button. macOS routes the custom scheme to the single Window scene, whose onOpenURL calls AppState.handleDeepLink, which recognises host=="auth-callback" and resumes the parked continuation. ## Accessibility

Weft's native app is a single-window SwiftUI 26 app (WeftApp.swift) that forces light appearance (`preferredColorScheme(.light)`, WeftApp.swift:46) and routes between SignIn / Teacher / Student flows with animated crossfades. Chrome is Liquid Glass (Glass.swift `weftGlass`, Components.swift `GlassCard`/`Chip`/`Kicker`/`WeftTopBar`) floating on a static MeshGradient `AmbientBackground`. The design system is a fixed token set: Theme.swift has 11 literal RGB colours, an absolute-point type scale (`Theme.sans(n)` / `Theme.serif(n)`), spacing and radii. The exam workspace (ExamView) is an HSplitView of an NSTextView-backed rich text editor (RichTextEditor.swift + WeftTextView.swift, with Google-Docs key equivalents handled in `performKeyEquivalent`) and a browser-style reference panel (ExamReferencePanel + ReferenceTabs) hosting PDFKitView and a whitelisted WKWebView (LockedBrowserView).
